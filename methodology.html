What this protocol measures

Functional compatibility

Authentication, one normal chat completion, optional tool calls, and optional streaming. A successful handshake is a starting point.

Real workload economics

Money spent on all attempts divided by successfully completed, equivalent jobs. Track retries and subscriptions separately.

Latency and reliability

p50 and p95 elapsed times across repeated runs, with error classes, request concurrency and client versions recorded.

Quality of outcome

Repeat the same acceptance tests against final artifacts. A valid API response is not necessarily a completed user task.

Start with one safe smokecheck

The included Python tool uses the standard library. It makes exactly one request to an OpenAI-compatible chat-completions endpoint. It does not create accounts, change provider settings, or store keys. If the provider bills requests, that one request may incur a charge.

  1. Choose a supported model and retrieve the provider's documented HTTPS base URL.
  2. Make its API key available to the command as an API_KEY environment variable using your password manager or a protected session. Keep it out of shell history and source files.
  3. Run a normal response check. If it passes, optionally test stream and tool separately.
  4. Read the JSON output. A passing smokecheck proves this specific request succeeded, not an availability percentage or guaranteed compatibility.
py -3 tools/api_smokecheck.py --base-url $ApiBaseUrl --model $ModelId --mode normal
py -3 tools/api_smokecheck.py --base-url $ApiBaseUrl --model $ModelId --mode stream
py -3 tools/api_smokecheck.py --base-url $ApiBaseUrl --model $ModelId --mode tool

These commands use PowerShell variables you populate from the provider documentation. For Unix shells, use python3 and your shell's variable syntax. The output omits the API key and response bodies, and reports provider token usage only when the provider supplies it.

Important: Some gateways use Anthropic-specific APIs or implement only part of the OpenAI protocol. A failure can reflect a protocol mismatch or model capability, not an overall service outage. Never publish a performance claim based on one smokecheck.

The reproducible comparison

  1. Freeze the inputs. Write a fixed collection of tasks, prompts, expected deliverables, versioned client configuration, region, concurrency and time window.
  2. Define success first. Use task-specific checks: correct tool-call parameters, a valid build or test result, the expected JSON schema, or another observable outcome.
  3. Run multiple comparable trials. Record start time, completion time, status, retry count, and any data needed to reproduce the result, without logging private user prompts or API credentials publicly.
  4. Classify failures. Distinguish authentication, rate limiting, routing, bad tool calls, timeouts and wrong answers. Label uncertain causes as unconfirmed.
  5. Normalize spend. Use bills or usage statements, including failed/retried attempts. Separate fixed subscriptions, taxes and credits that distort per-request prices.
  6. Compare and retest. Publish p50/p95 with sample size and the actual workload, then repeat at another time. A single result is a snapshot.

Metrics worth recording

MeasureDefinitionWhy it matters
Completion rateSuccessful jobs ÷ attempted jobsA cheap partial answer is not an accomplished task.
Cost per completionTotal billed spend ÷ successful jobsIncludes the real cost of failures and retries.
p50/p95 latencyMedian/95th-percentile completion times, with sample countShows typical and tail behavior; don't confuse with time to first token.
Retry overheadExtra attempts ÷ initial attemptsReveals hidden request multiplication.
Tool-call accuracyTool calls meeting the expected schema and intentGates automation reliability beyond plain chat.
Quota behaviorActual 429s, rate headers, cooldowns and billing limitsPublished caps can differ from real workload capacity.
